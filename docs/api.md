# API Reference — simintech-api

Все классы доступны из корня пакета: `from simintech_api import ...`.

---

## COMClient

Низкоуровневый доступ к серверу `IMVTU_Server` (out-of-proc, `mmain.exe`).
Основа библиотеки: работает через **comtypes** (не pywin32) — структура
`TDataDescriptor` (`VT_RECORD`) маршалится корректно только через comtypes.

```python
from simintech_api import COMClient

client = COMClient(silent_mode=True).connect()   # скрытый UI
client.get_process_id()                          # PID mmain.exe
client.disconnect()
```

### Методы
| Метод | Описание |
|---|---|
| `connect() -> COMClient` | Подключиться (требует `mmain.exe /regserver`). Бросает `ComConnectionError` вне Windows. |
| `disconnect()` | Отсоединиться (приложение не закрывается). |
| `shutdown(kill_pids=None)` | Отсоединиться и, если передан `kill_pids`, завершить **только** эти процессы `mmain.exe`. По умолчанию процессы не завершаются. |
| `call(method, *args) -> Any` | Вызвать любой метод `IMVTU_Server`. |
| `open_project(path) -> int` | Открыть проект, вернуть ProjectId. |
| `new_project() -> int` | Создать новый проект, вернуть ProjectId. |
| `get_process_id() -> int` | PID процесса SimInTech. |
| `find_signal(name, project_id) -> TDataDescriptor` | Найти сигнал. |
| `connected`, `is_available` | Свойства состояния. |

> **`shutdown()` по умолчанию процессы не завершает.** Библиотека не решает за
> вызывающего, какие `mmain.exe` можно убивать: она не трогает процессы,
> запущенные пользователем. PID передаёт вызывающий — свой берётся из
> `get_process_id()`, а чужие — из списка «появившихся после начала работы»
> (так делает `tests/conftest.py`): `client.shutdown(kill_pids=[pid])`.

## Project

```python
prj = Project.from_template(client)    # проект из шаблона — только такой считает
prj.set_calc_end_time(10.0)            # конечное время расчёта (endtime слоя)
prj = Project.open(client, "model.prt")
prj.save_xml("out.xprt")               # / save_binary("out.prt")
prj.close()
```

> `Project.new(client)` создаёт **пустой** проект — без расчётного слоя и
> настроек расчёта. В нём модельное время не растёт, хотя `run`/`step`/`run_to`
> сообщают об успехе, а `get_time()` остаётся `0.0`. Для расчёта — только
> `from_template` и явный `set_calc_end_time` (иначе берётся значение шаблона,
> 10 с).

### Методы
| Метод | Описание |
|---|---|
| `new(client)` | Создать **пустой** проект: расчётного слоя в нём нет, модельное время не растёт. Для расчёта — `from_template`. |
| `from_template(client, template=None)` | Проект из шаблона пустой модели (`find_model_template()`): с расчётным слоем, расчёт в нём идёт. |
| `open(client, path)` | Открыть проект (.prt/.xprt). |
| `set_calc_end_time(seconds)` | Задать конечное время расчёта (`endtime` слоя); требует проекта с расчётным слоем. |
| `calc_settings() -> dict` | Параметры расчётного слоя (из выгрузки `.xprt`). |
| `set_calc_setting(name, value)` | Записать параметр расчёта (`SetLayerProp`), проверив имя. |
| `save_xml(path) / save_binary(path)` | Сохранение. |
| `close()` | Закрыть проект. |
| `get_main_page() -> Page` | Главная страница. |
| `get_current_page() -> Page` | Текущая страница. |
| `find_signal(name) -> TDataDescriptor` | Поиск сигнала по имени записи (FindSignalData; SignalError, если нет сигнала или нет базы сигналов). |
| `signal(name) -> Signal` | Объект Signal для чтения/записи. |
| `list_signals() -> list[SignalInfo]` | Список сигналов: сначала обменные (COM), при пустом — имена из `.xprt` (fallback). |
| `get_signal_names_from_xml() -> list[str]` | Имена сигналов из XML-представления проекта (`.xprt`). |
| `simulation() -> Simulation` | Управление расчётом. |
| `run() / stop()` | Удобные обёртки расчёта. |

### Свойства
`id`, `client`.

## Page

```python
page = prj.get_main_page()
b1 = page.create_block("Константа", 0, 0)         # x,y — координаты
b2 = page.create_block("Усилитель", 200, 0, width=60, height=40)
```

### Методы
| Метод | Описание |
|---|---|
| `activate()` | Сделать страницу текущей (SetCurrentPage). |
| `create_block(class_name, x, y, *, width, height, layer_no, parent_block) -> Block` | Создать блок. Бросает `UnsupportedBlockError` для классов из `UNSUPPORTED_COM_BLOCK_CLASSES`. |
| `get_blocks() -> list[Block]` | Все блоки текущей страницы. |
| `find_block(name) -> Block | None` | Поиск по свойству Name. |
| `create_wire(start_port, end_port, points=None, *, wire_type, layer_no) -> Wire` | Линия между портами. `points` — опорные точки, но **маршрутом они не управляют** (его задаёт SimInTech); при передаче выдаётся `UserWarning`, см. раздел Wire. |

## Block

```python
b1 = page.create_block("Константа", 0, 0)
b1.set_property("a", 5.0)               # значения приводятся к строке
b1.set_property("a", [1, 1, 1])         # массивы тоже (здесь — для примера)
name = b1.get_property("Name")          # чтение как str
b1.set_position(left, top, width, height, angle)
b1.set_center(cx, cy, width, height)    # по центру
b1.get_in_port(0) / b1.get_out_port(0)  # порты (0-based, с fallback-паттерном)
b1.connect(b2)                          # out0 -> b2.in0
```

### Методы
| Метод | Описание |
|---|---|
| `set_property(name, value) -> Block` | Установить свойство (значение → строка). |
| `get_property(name) -> str` | Прочитать свойство как строку. |
| `get_name() / set_name(name)` | Свойство Name. `set_name` через COM **не переименовывает** блок (имя остаётся автоматическим, `k_0`): фактическое имя берите из `get_name()` — по нему блок и адресуется. |
| `get_points() -> str` | Сырое значение Points. |
| `set_position(x, y, *, width, height, angle)` | Left/Top/Width/Height/Angle. |
| `set_center(cx, cy, *, width, height)` | По центру. |
| `get_port_count() / get_block_port(i)` | Общий доступ к портам. |
| `get_in_port(i) / get_out_port(i)` | Входные/выходные порты. |
| `get_ports() -> list[Port]` | Все порты. |
| `connect(other, out_index=0, in_index=0) -> Wire` | Соединить. |
| `class_name` | Свойство имени класса. |

## Port

```python
p = b1.get_out_port(0)
info = p.get_info()          # PortInfo (12 полей)
name = p.get_name()
side = p.get_side()          # PortSide (LEFT/RIGHT/TOP/BOTTOM)
x, y = p.get_coords()        # глобальные координаты для трассировки
p.set_name("u") / p.set_side(PortSide.RIGHT) / p.set_mode(mode)
p.connect(other_port)        # источник -> приёмник
```

### `PortInfo` (dataclass)
`port_id, name, side, mode, type_id, item_id, is_inverse, is_center, is_invisible, x, y, x_global, y_global`.

## Wire

```python
w = page.create_wire(p1, p2)                  # маршрут — за SimInTech
w = page.create_wire(p1, p2, [(50, 20)])      # точки уйдут в COM, но не в маршрут
w.set_points([(10, 20), (30, 40)])            # то же: выдаёт UserWarning
w.normalize()                                 # выровнять (NormalizeWire)
w.branch_to(port, point_index=0)              # ветвление от линии
```

**Геометрию линии задаёт SimInTech, а не вызывающий.** Нормализация
(`NormalizeWire` после перерисовки редактора) ломает линию на ортогональные
участки сама и препятствия не учитывает; `SetWirePoint` на линии без
размеченных точек игнорируется, а на размеченной вставляет точку в ломаную —
линия идёт назад (зигзаг). Способа задать свои изломы в API нет. Поэтому
`create_wire(points=…)` и `set_points(…)` не управляют маршрутом (об этом
выдаётся `UserWarning`), а чистая схема получается **расстановкой** блоков
(`LayeredPlacer`): источник с единственным приёмником — вплотную к нему.

## Signal

```python
sig = prj.signal("CoolTT_C_D_SySt_TechSt")
value = sig.read()                # по DataType (float/int/bool/str)
sig.write(3.14)

arr = sig.read_array()            # массивы (ARRAY/INT_ARRAY)
sig.write_array([1.0, 2.0, 3.0])
sig.array_count() / sig.set_array_count(n)
```

Типы (`DataType`): `DOUBLE=0`, `INTEGER=1`, `BOOL=2`, `STRING=4`, `ARRAY=5`, `INT_ARRAY=12`.
Чтение/запись диспетчеризуются автоматически. Запись в bool/int — `int(value)`, в double — `float(value)`.

## ScriptBridge

Выполняет код встроенного языка внутри открытого проекта и возвращает то, что
скрипт записал в файл. Нужен там, где COM-интерфейса не хватает: топология
(порты и линии связи), удаление объектов, всё, что есть в языке и отсутствует в
`IMVTU_Server`.

```python
from pathlib import Path

from simintech_api import COMClient, Project, ScriptBridge

client = COMClient().connect()
project = Project.from_template(client)
project.set_calc_end_time(1.0)

bridge = ScriptBridge(client, project.id)
result = bridge.run_probe(
    'writelnutf8(fid, "objects=" + floattostr(getobjcount(getcurrentcontainer)));',
    Path(r"C:\Temp\probe.txt"))

print(result.lines)              # ['objects=7']
```

Неполный результат `run_probe` не возвращает: если пара маркеров не сошлась,
это `ScriptBridgeError`, а не флаг. Проверять `result.complete` вызывающему не
нужно — при успешном возврате он всегда истинен.

**Чем тело пишет результат.** Тело может писать через `fid` — это имя связано с
дескриптором моста, и так написаны все пробы. Но отдельной области видимости для
него у языка нет: вложенная процедура видит и изменяет переменные охватывающего
блока, а тень имени во вложенном блоке отвергается компилятором. Поэтому
дескриптор моста живёт под именем, порождённым меткой запуска, и чужому тексту
недоступен, а `fid` — приманка. Если тело зовёт чужой код, присваивающий `fid`
(так делает вендорская `export_1layer_topology`), то **после** такого вызова
писать надо через `br_writeln(...)`: приманка к тому моменту указывает на чужой
файл. Измерения и границы —
`docs/superpowers/specs/2026-09-24-script-bridge-fid-ownership.md`.

**Как это работает.** `SetPageScript` кладёт текст скрипта в страницу проекта,
`ProjectStart`+`ProjectStep` запускают расчёт, скрипт исполняется на первом шаге
и пишет результат в файл, который затем читается.

**Почему устроено именно так.** Контракт измерен на живом SimInTech64
(`docs/superpowers/specs/2026-09-21-script-bridge-design.md`):

- `SetPageScript` возвращает `1` **всегда** — и при синтаксически неверном
  скрипте тоже, поэтому код возврата как признак успеха бесполезен;
- ошибка скрипта наружу не сообщается: синтаксическая молча останавливает
  расчёт (`ProjectStart`/`ProjectStep` успешны, модельное время стоит на нуле),
  ошибка времени выполнения молча обрывает остаток скрипта;
- `SetPageScript` **перезаписывает** прежний скрипт страницы; пустая строка его
  очищает.

Отсюда три проверки, которые `run_probe` делает всегда: маркер завершения в
файле результата (`result.complete`), рост модельного времени и возврат
прежнего скрипта — в `finally`, потому что возврат нужен и при отказе.

> ⚠ `result.complete == False` означает, что скрипт оборвался и строки
> **неполны**. Использовать их как полный результат нельзя — именно на этом
> мост и был бы обманут, если бы доверял факту отсутствия ошибки.

Файл по `result_path` может существовать до вызова — он удаляется, чтобы старый
результат не был принят за новый.

### Жизненный цикл расчёта

Проба **запускает расчёт сама** и обязана вернуть проект в «остановлен».
Контракт измерен 2026-09-22
(`docs/superpowers/specs/2026-09-22-script-bridge-lifecycle-design.md`):

- пока проект инициализирован (`GetProjectStateFlag != 0`; на живом стенде это
  `1` после `ProjectStart` и `7` после шага), среда **отвергает добавление
  блока к схеме**, и отказ приходит **модальным окном** «Установка блока на
  схему в процессе моделирования запрещена». Внешний COM-клиент снять его не
  может: вызов стоит, пока окно не закроет человек — это и выглядело как
  «зависание ~150 с»;
- `ProjectPause` **не заменяет** `ProjectStop`: при паузе правка так же
  отвергается;
- `ProjectStart` — это **инициализация** (вендорский `helpstring`), и модельное
  время при этом **сбрасывается**: проба на уже идущем расчёте его уничтожает;
- `ProjectStop` безвреден на остановленном проекте, идемпотентен, модельное
  время не сбрасывает.

Поэтому `run_probe` останавливает расчёт на **каждом** пути, где вызывал
`ProjectStart` (включая случай, когда тот бросил: состояние тогда неизвестно, а
остановка безопасна), **подтверждает** остановку чтением флага и **не
утверждает** её, если флаг прочитать не удалось. Порядок внутри `finally` —
сначала остановка, затем возврат скрипта; сбой одной операции не отменяет
другую, и сбой остановки не описывается словами о потере скрипта.

**На идущем расчёте проба отказывает.** Первым действием читается
`GetProjectStateFlag`; `state != 0` — отказ `ScriptBridgeUnsafeStateError`, и
проект остаётся нетронутым. Иначе проба уничтожила бы расчёт вызывающего:
`ProjectStart` — это инициализация, а она обнуляет модельное время. Нечитаемое
состояние — тоже отказ: «не знаю» здесь неотличимо от «идёт расчёт». Цена
решения названа прямо: «сначала `run`, затем чтение топологии» требует явной
остановки расчёта между ними.

## read_topology

Читает топологию **текущего контейнера** проекта: объекты, их порты и связи.
Работает поверх `ScriptBridge`, и причина не в отсутствии портовых методов — они
в COM есть (`GetPortCount`, `GetBlockPort`, `GetInPort`/`GetOutPort`,
`GetPortInfo` с режимом и стороной). В COM **нет связности**: отдельных методов
для портов связи в интерфейсе нет (`GetPortWireId` и подобные — функции
встроенного языка, не COM), прочитать линию как пару «откуда → куда» нечем,
`Points` у линии пуст даже после `NormalizeWire`, а у портов нет читаемых
свойств — поэтому линия и возвращается без концов.

```python
from pathlib import Path

from simintech_api import COMClient, Project
from simintech_api.core.topology import read_topology

client = COMClient().connect()
project = Project.from_template(client)
project.set_calc_end_time(1.0)
page = project.get_main_page()
page.create_block("Ступенька", 0, 0).connect(page.create_block("Усилитель", 200, 0))

topology = read_topology(client, project.id, Path(r"C:\Temp\topology.txt"))

for row in topology.objects:                 # kx_0 Усилитель
    print(row.name, row.class_name)
for port in topology.ports:                  # kx_0 1 in inport
    print(port.object_name, port.index, port.direction, port.name)
for link in topology.connections:            # Step_source_1.0 — kx_0.1
    print(link.object_a, link.index_a, link.object_b, link.index_b)
```

`result_path` — рабочий файл: мост пишет в него результат пробы, удаляя прежний.

**Проект обязан считать.** `read_topology` идёт поверх `ScriptBridge`, а тот
требует роста модельного времени (раздел ScriptBridge). Если проект не считает —
у проекта из `Project.new()` нет расчётного слоя, а расчёт собранной модели молча
останавливает неподключённый вход, — отказ придёт как `ScriptBridgeError` про
**нерастущее модельное время**, и текст его указывает на скрипт («проверьте
синтаксис пробы»), хотя проба тут ни при чём: об остановке расчёта среда не
сообщает.

**Что читается.** Только текущий контейнер: субмодели не обходятся, координаты
не читаются — ни блоков, ни портов. Топология не меняется: проба только читает.

Внутренняя страница читается, если сделать её текущей через COM
(`Project.submodel_page(block.id)` и `Page.activate()`). Измерено: на демо вендора
проба вернула оттуда 35 объектов, 64 порта и 32 связи — те же числа, что в
эталонной выгрузке скрипта вендора, но у чисел там **другой смысл**: в выгрузке
64 — записи о **портах с проводом** (ещё 64 записи `ConnectedTo` — это 32 связи,
каждая с обоих концов), а проба печатает **все** порты отобранных объектов.
Совпали 64 потому, что на этом демо у всех отобранных блоков провод есть: на
модели из двух блоков у `kx_0` порт 0 без провода, и проба вернула 3 порта при
1 связи.

**Скрипт страницы при чтении не теряется.** Мост опознаёт ту страницу, в которую
сам и писал: снимает скриптовые записи проекта до установки пробы, ставит пробу с
уникальной меткой, снимает второй раз — и возвращает прежний скрипт в ту запись,
которая изменилась ровно одна и несёт метку. Раньше прежний скрипт читался с
**главной** страницы и возвращался в текущую, из-за чего скрипт внутренней
страницы терялся: на демо вендора 939 символов вендорского скрипта экспорта
топологии заменялись пустотой при полностью успешном чтении. Закреплено живым
тестом `test_reading_topology_inside_container_keeps_its_script`.

Одна оговорка остаётся, и снять её проверкой нельзя: опознание опирается на то,
что запись, в которую попала метка, — это запись **той же** страницы.
Идентификаторов страниц в выгрузке нет, поэтому свойство не выражается ни кодом,
ни юнит-тестом; оно измерено (двумя разными скриптами на двух страницах, плюс
обход 1534 страниц поставки). Расширять замеры на другие модели — до того, как
топология поедет в MCP.

**Что возвращается.** `Topology` — три списка: `objects` (`ObjectRow`: имя,
класс), `ports` (`PortRow`: имя объекта, индекс, направление, имя порта),
`connections` (`Connection`: два конца вида `(имя объекта, индекс порта)`). Типы
и ключ связи лежат в `simintech_api.topology`. Направление порта — `in`, `out`
или `undirected` (режим из `getportinfo`: 0 — вход, 1 — выход, 2 —
ненаправленный; справка знает только эти три). Режим вне 0/1/2 проба пишет в поле
направления **сырым числом**, и разбор отказывает: дрейф контракта виден отказом,
а не подменой на `undirected`. Здесь проба строже скрипта вендора, который пишет
`undirected` на всё, что не 0 и не 1. Цена отступления измерена и на штатных
данных равна нулю: 1337 портов 70 демо-моделей дали режимы 0 (586), 1 (448) и
2 (303), а значений вне этих трёх — ни одного.

Отображение сверено и **живьём**: на демо поставки направление каждого порта
сравнивается с режимом того же порта из COM (`GetPortInfo().Mode`), и `undirected`
берётся оттуда, где он есть сам, — на модели из четырёх объектов с четырьмя
ненаправленными портами. Сделать такой порт нарочно **нельзя**: `SetPortMode` с
режимом 2 на порту блока останавливает расчёт модели — измерено контрольным
опытом на двух одинаковых проектах: перестановка режима **на то же значение**
расчёт не трогает, а на 2 — останавливает, и мост отказывает про нерастущее
модельное время. Режим порта — часть интерфейса блока, а не его свойство.

**Связи канонизированы.** Одна и та же пара портов может прийти двумя
записями-зеркалами — как `(A, i, B, j)` и как `(B, j, A, i)`. Это дедупликация
**представления**, а не утверждение о симметрии `traceallports`: на парной линии
он и правда даёт связь с обоих концов (измерено), а после вендорского правила
кратности входной порт берёт только первого соседа, и симметричности наблюдения
на развилке никто не обещает — несимметричность измерена на T2.
Разбор кладёт их в словарь по каноническому ключу `connection_key` (концы
упорядочены по имени объекта и индексу), и в `connections` остаётся **одна**
запись — сам канонический ключ. Поэтому `Topology.connections` детерминирован:
для одного и того же графа он одинаков независимо от порядка обхода портов, и
равные связи равны как значения. Значим по-прежнему ключ, а не `object_a`:
`Connection("B", 1, "A", 0)` и `Connection("A", 0, "B", 1)` — одна связь с
разными значениями, и сравнивать их надо через `connection_key`.

**Что считается объектом.** Объекты, прошедшие **критерий допустимости**, — он
один на все три места фильтрации и живёт в
`simintech_api.topology.ELIGIBLE_OBJECT_TYPES`. Критерий: среда однозначно
адресует объект, перечисляет его порты, `getportindex(getblockportid(obj, i)) = i`,
`getportwireid` и `getportinfo` к нему применимы, и он не линия и не
презентационная инфраструктура. Сейчас это типы **100, 102, 104 и 106**.

Прежде признак назывался вендорским (`export_sheme_functions.inc:44-50` — только
100 и 102). Теперь вендорская выгрузка — **oracle пересечения, а не норматив**:
она допускает ссылку на необъявленный объект (измерено: `ConnectedTo` на
`TimeGraphic_0` при одном объявленном `Step_source_1`), а наш разбор такой ссылки
не допускает — у нас второй конец объявляется.

Измерено 2026-09-23 переписью по классам: 100 (в том числе трёхпортовый
«Сумматор»), 104 («В память») и 106 («Временной график») проходят все четыре
условия; 102 оставлен по прежнему основанию — субмодели демо и сверка с эталоном.
Отсекаются они **данными, а не списком**: у линии адресация не держится —
`getportindex(getblockportid(wire, 1))` вернул 2, а не 1 (живой тест
`test_line_fails_addressing_round_trip`); подпись имеет ноль портов. Классы 105,
109 и 113 в набор не входят потому, что их **нельзя создать** — измерить не на
чем, и это другое основание, чем отказ по критерию.

**Что даёт отбор.** Без него в объекты попадали линии и подписи, а линия
становилась ещё и **концом связи**: у неё есть свои порты, и связи к ней давали
лишние рёбра. Перемерено 2026-09-23: на контейнере демо 68 объектов и 96 связей
против 35 и 32; на проекте из двух блоков и одной линии — 4 объекта, 5 портов и
3 связи против 2 объектов и 1 связи, и обе лишние ведут к объекту линии.

Связь с **непрошедшим** критерий объектом при этом **тихо теряется**, и это
осознанный выбор:
`traceallports` отдаёт соседей независимо от их типа, поэтому без проверки
второго конца связь попала бы в протокол, сославшись на необъявленный порт, —
и разбор отверг бы модель **целиком**, не сообщив ничего. Молча потерять одно
ребро лучше, чем не прочитать модель.

**Второй конец отсекается ещё и по контейнеру.** `traceallports` отдаёт соседей и
из других контейнеров, а такой сосед в фазе объектов не объявлен — и связь на
него отвергла бы результат целиком. Поэтому у соседа сверяется владелец:
`getownercontainer(сосед) = getownercontainer(объект)`. Форма взята у вендора
(`export_sheme_functions.inc:107`) и сравнивает владельцев **двух объектов**, а не
владельца соседа с текущим контейнером: `getownercontainer` и
`getcurrentcontainer` не обязаны совпадать на верхнем уровне страницы. Цена та же,
что у фильтра по типу, — связь через границу контейнера тихо теряется. Живого
воспроизведения у этого стража нет: на демо вендора связей наружу не нашлось.

**Кратность связей у входа взята у вендора.** Вендор берёт у входного порта не
больше одного соседа (`min(1, cols(conn_port_list))`, `:99`), у остальных портов —
всех, и проба воспроизводит это правило с 2026-09-23. Прежде она брала всех у
любого порта и называла это осознанным расхождением; оно снято, потому что
оказалось **другим множеством связей**, а не другой формой записи. Цена прежней
редакции измерена на развилке: `traceallports` отдаёт не соседа, а **всю связную
компоненту**, поэтому вход называл соседом и брата по разветвлению, и в протоколе
появлялось ребро вход–вход, которого в вендорской выгрузке нет. На демо вендора
обе редакции **неразличимы** — у всех 32 линий там ровно два конца, — и потому
прежняя проходила сверку с эталоном: эталон различает форму развилки, а не
кратность.

**Форму линии `connections` не описывает, и это граница контракта.** Кратность
соседей взята у вендора, поэтому одна разветвлённая линия и две отдельные линии с
тем же составом концов дают **одно и то же** множество связей — измерено живьём на
двух фикстурах (`test_branch_shapes_give_the_same_connections`). Читать это поле
как обратимое описание проводки нельзя. Для анализа структуры проводки нужен
wire-level API; исследованные `getportwireid` и `tracestartportwires` дают для
этого исходные данные, но достаточность их сочетания для восстановления проводки
**не доказана** — это поле отвечает на вопрос «что с чем соединено», а не «как
это проложено».

Вопрос того же рода, про индекс порта, закрыт отдельно: индекс порта в фазе
портов — счётчик цикла, а у соседа — `getportindex`, и это тождество **измерено**
2026-09-23 (`test_port_index_round_trip_is_identity`) и подтверждено вендорской
справкой, дающей тот же обратный переход примером. Граница у него названа: вне
фильтра типов 100/102 тождество не выполняется — на объекте линии `getportindex`
вернул разные номера для одного и того же, поэтому фильтр держит не только
состав объектов, но и достоверность адресации портов.

**Отказ — это отказ, а не пустая топология.** Разбор строгий: неверное число
полей, неизвестный тип строки, ссылка на необъявленный объект или порт,
дубликаты, петля — всё это `TopologyError`.

Пустой `Topology` означает: **на странице нет объектов, прошедших критерий
допустимости**, то есть проба не нашла ничего, что считает моделью. Контейнер,
все объекты которого отсеял фильтр, даёт пустую топологию — неотличимо от честно
пустой. Прежний пример («страница с единственным блоком «В память» читается как
0 объектов») **перестал быть верным 2026-09-23**: этот тип теперь проходит
критерий, и такой странице соответствует 1 объект. Замена ему отдельным замером
не подтверждена, и это сказано прямо. Поэтому на пустую
топологию нельзя смотреть как на «объектов нет»: она говорит лишь о том, что
среди отобранных типов их нет.

Разбор возвращает пустую топологию только на честно пустом результате, а отказ —
на сломанном: иначе провал разбора выглядел бы как такая же пустота, и вызывающий
не отличил бы «прочитать не удалось» от «там ничего нет». Класс свой, а не
`ValueError`: это отказ данных из среды, и отличать его от ошибок собственного
кода вызывающий обязан. Отказ самого транспорта подмене не подлежит: неполадки
моста приходят `ScriptBridgeError`.

Класс объекта — тот, что сообщил **язык**, а не COM: для блока-плагина
`Block.class_name` возвращает имя плагина, поэтому расхождение классов —
находка, а не отказ.

## read_model_overview

Отвечает на вопрос **«что представляет собой эта модель и как она устроена»**:
объекты текущего контейнера с их портами, связи между ними и подпись области
обзора. Слой **не делает собственных COM-вызовов** — он читает топологию тем же
`read_topology` и группирует её: порты раскладываются по объектам, связи
переносятся как есть.

```python
from pathlib import Path

from simintech_api import COMClient, Project
from simintech_api.core.semantic import read_model_overview
from simintech_api.semantic import ContainerRef, overview_to_dict

client = COMClient().connect()
project = Project.from_template(client)
project.set_calc_end_time(1.0)
project.get_main_page().create_block("Ступенька", 0, 0)

overview = read_model_overview(client, project.id, Path(r"C:\Temp\o.txt"),
                               container=ContainerRef.main())

overview.object_count, overview.port_count          # 1, 1
overview.objects[0].ports[0].direction              # 'out'
overview_to_dict(overview)["summary"]               # {'objects': 1, ...}
```

Порты — те же `PortRow`, что и в топологии, объекты и связи тоже не
переупакованы: второй тип с тем же смыслом разошёлся бы с первым молча.
`overview_to_dict` даёт JSON-готовую форму для адаптера (MCP), чтобы тому не
пришлось знать ни COM, ни типов топологии.

**`container` обязателен, и это не придирка.** Данные описывают **текущий**
контейнер — тот, в который вошли `activate()`/`submodel_page()`, — а
идентификатора контейнера среда в Python не отдаёт: `getcurrentcontainer` и
`getownercontainer` живут только внутри тела пробы, COM-метода «какой контейнер
текущий» нет. Значит, подпись обзора — утверждение вызывающего, а значение по
умолчанию означало бы подписывать обзор субмодели именем главной страницы.

```python
project.submodel_page(block.id).activate()
read_model_overview(client, project.id, path,
                    container=ContainerRef.submodel(block.id, block.get_name()))
```

**Что не входит.** Иерархия контейнеров не строится: вложенность измерена только
на одном уровне, `Page.parent()` — предположение, перечисления контейнеров в COM
нет вовсе. Связи — тот же `Connection` топологии, то есть «что с чем соединено»,
а не восстановление проводки (кратность вендорская, форма линии теряется).
Изменение модели сюда не входит: слой только читает. Границы целиком —
`docs/superpowers/specs/2026-09-24-semantic-model.md`.

### inspect_object

Досмотр одного объекта: его порты и связи с соседями. **Тоже без COM** — это
проекция уже прочитанного обзора, а не отдельный вызов; спрашивать можно по
любому объекту, который в обзоре есть.

```python
from simintech_api.semantic import inspect_object, inspection_to_dict

inspection = inspect_object(overview, "Integrator_0")
inspection.object.ports[0].direction        # 'in'
inspection.object.in_ports                  # 1
inspection.peers[0]                         # PortPeer(port_index=0, object_name=...)
inspection_to_dict(inspection)["peers"]     # [{'port': 0, 'peer': {...}}]
```

Сосед назван **своим** концом связи: `peers[i].port_index` — наш порт,
`object_name`/`index` — второй конец. Слова «источник» и «приёмник» здесь
неуместны: концы связи неориентированы, и вендорская кратность (на входной порт
идёт один сосед, на остальные — все) делает направление ненадёжным признаком.

Неизвестное имя — отказ (`ValueError` с перечнем известных имён), а не пустой
ответ: «объекта нет» и «объект есть, но связей нет» — разные состояния.

### inspect_port

Досмотр одного порта: он сам и его связи. Тоже **без COM** — проекция обзора.

```python
from simintech_api.semantic import inspect_port, port_inspection_to_dict

port = inspect_port(overview, "Integrator_0", 0)
port.port.direction            # 'in'
port.port.name                 # имя порта, как его сообщил язык
port.peers                     # [PortPeer(port_index=0, peer_object=..., peer_index=...)]
port_inspection_to_dict(port) # {'object': ..., 'port': {...}, 'peers': [{...}]}
```

Адрес порта — пара **(имя объекта, индекс)**, а не имя: индекс и есть адрес в
протоколе. Отказы различают два состояния: объекта с таким именем нет и у
объекта нет порта с таким индексом. Порт без связей — не отказ: это обычное
состояние модели.

**Направление связи не выводится.** Догадка «вход принимает, выход отдаёт» здесь
не делается: концы связи неориентированы, а вендорская кратность (на входной порт
идёт один сосед, на остальные — все) делает направление ненадёжным признаком.
Соседи перечисляются как есть, и связей у порта может быть **сколько угодно** —
«один порт — одна связь» не предположение слоя.

### query_connections

Связи **между двумя названными объектами**. Тоже **без COM** — отбор по уже
прочитанному обзору, а не отдельный вызов.

```python
from simintech_api.semantic import query_connections, connection_query_to_dict

query = query_connections(overview, "Integrator_0", "Step_source_1")
query.links                      # [Connection(object_a=..., index_a=..., ...)]
connection_query_to_dict(query)  # {'between': ['Integrator_0', 'Step_source_1'],
                                 #  'connections': [{'a': [...], 'b': [...]}]}
```

Отвечает **связями, а не соседями**: у каждой возвращённой связи названы оба
конца, поэтому между одними и теми же объектами видно каждую пару портов, а не
«ещё одного соседа». Порядок в вопросе ничего не значит — `query_connections(
overview, "B", "A")` даёт те же связи, — а сами `links` остаются в порядке
разбора: концы в них нейтральны (`a`/`b`), как и в обзоре.

Адрес здесь — **имя объекта**, а не пара (имя, индекс): индексы портов видны в
самих связях. Связь объекта с самим собой спрашивается тем же вызовом и **не**
смешивается со связями с соседями.

Отказы: имени нет в обзоре — `ValueError` с перечнем известных имён, и
проверяются **оба** названных конца: иначе «нет объекта» указывало бы на первый
из двух, а про второй нельзя было бы отличить «его нет» от «он есть, но связи
нет». Отсутствие связи — не отказ, а обычное состояние модели: `links == []`.

Имена и числа в примере — форма ответа, а не замер. Что подтверждается живьём:
`test_query_connections_matches_vendor_reference` сверяет связи пары с эталоном
вендора внутри контейнера и проверяет инвариант досмотров в обе стороны —
каждая возвращённая связь видна досмотром обоих своих концов, и обратно;
`test_query_connections_on_own_project_sees_the_wire_we_made` сверяет со связью,
которую тест провёл сам через COM. Сам запрос — отбор из уже прочитанного
обзора, поэтому равенство «обзор ↔ эталон» измеряет соседний
`test_model_overview_matches_vendor_reference_inside_container`, а не эти тесты.

## Layout

### LayeredPlacer — расстановка блоков слоями
```python
from simintech_api.layout import LayeredPlacer
placer = LayeredPlacer()
positions = placer.place(
    block_ids=["A", "B", "C"],
    connections=[("A", "B"), ("B", "C")],
    sizes={"A": (60, 40), "B": (60, 40), "C": (60, 40)},
    origin=(0.0, 0.0),
)  # -> {"A": (cx, cy), ...}
```
Алгоритм: ранжирование (слои по X) → медианная эвристика (порядок в слое) →
координаты с учётом размеров. Обратная связь и чистые циклы поддерживаются
(цикл размещается, корень — блок с минимумом входов).

### ObstacleGrid — сетка препятствий
```python
from simintech_api.layout import ObstacleGrid
grid = ObstacleGrid(200, 120)          # 200x120 узлов, шаг 20 px
grid.add_rect(x, y, w, h, label="block")   # блок с отступом 1 узел
grid.add_point(x, y, label="wall")         # точечное препятствие
grid.is_blocked(gx, gy)                    # проверка узла
grid.to_grid(x, y) / grid.to_scheme(gx, gy)  # конверсия координат
```

### AStarRouter — расчёт ортогонального маршрута
```python
from simintech_api.layout import AStarRouter
router = AStarRouter(grid_size=20, turn_penalty=2.0)
points = router.route(
    (x1, y1), (x2, y2), grid,
    start_side=1,  # PortSide правого порта
    end_side=0,    # PortSide левого порта
)  # -> список опорных точек (может быть [] — прямое соединение)
```
Свойства: ортогональное движение (4 направления), штраф за повороты,
сглаживание коллинеарных точек, «вылет» из порта по нормали к стороне.
`LayoutError` — путь невозможен.

Это **только расчёт**: геометрию линии задаёт SimInTech, и применить к ней
`points` нечем (см. раздел Wire).

## Исключения

| Класс | Родитель | Когда |
|---|---|---|
| `SimInTechError` | Exception | базовое |
| `ComConnectionError` | SimInTechError | нет COM (не Windows / не зарегистрирован) |
| `ComCallError` | SimInTechError | ошибка вызова метода (method, hr) |
| `ProjectError` / `PageError` | SimInTechError | проект/страница |
| `BlockError` | SimInTechError | блок |
| `UnsupportedBlockError` | BlockError | класс блока отвергнут библиотекой (COM его создаёт) |
| `PortError` / `WireError` | SimInTechError | порт/линия |
| `SignalError` | SimInTechError | сигнал (не найден/неверный тип) |
| `SimulationError` | SimInTechError | расчёт |
| `LayoutError` | SimInTechError | путь/размещение невозможны |
