# Пилот функциональной семантики Model IR

Статус: черновик на проверку. Дата: 2026-10-30.

## 1. Зачем

Model IR уже отвечает на структурные вопросы: что с чем соединено, какие
объекты достижимы, где разрыв. Но `trace_signal` проходит и по рёбрам
`kind="block"`, которые `ModelIndex` добавляет между каждым входом и каждым
выходом обычного блока. Для связности это верно, для причинного анализа нет:
структурно допустимый путь выдаётся за функциональное влияние.

Инженеру нужен ответ другого уровня: какие входы действительно влияют на
выбранный выход, какие зависимости безусловные, какие условные, какие зависят
от состояния, какие заданы скриптом и какие остаются неизвестными. У каждого
утверждения должен быть провенанс.

Пилот охватывает десять классов в семантическом эталоне и девять в живой
приёмке на модели электропривода. Он должен дать проверяемую семантическую
основу, а не полную математику всех 958 классов.

## 2. Цель

На модели `electric-drive-ad-480kw.prt` и на девяти живых классах:

1. Отвечать на запрос о влиянии входов на выбранный выход по всей модели,
   включая границы субмоделей.
2. Различать безусловные, условные, управляющие и зависящие от состояния
   зависимости.
3. Помечать зависимости, заданные скриптом, как неизвестные, пока скрипт не
   разобран и не подтверждён.
4. Показывать неизвестные участки прямо в ответе, а не только в сводке.
5. Указывать происхождение каждого существенного утверждения: контракт,
   инженерная таблица или эксперимент.
6. Давать `semantic_coverage`, отделяющую разобранную структуру от известной
   функциональной семантики.

## 3. Не цели

- SystemPlan и компиляция требований в архитектуру.
- Полная функциональная семантика всех классов каталога.
- Автоматический разбор скриптов «Языка программирования».
- Произвольные расчётные assertions и динамическая верификация свойств.
- Замена инженерной проверки экспериментом.
- Рекурсивное раскрытие всех внешних библиотек в один IR.

## 4. Анти-цели

Пилот считается провалившимся, если:

- структурная достижимость выдаётся за доказанное причинное влияние;
- неизвестное поведение достраивается по имени класса или по аналогии;
- эксперимент в одном сценарии превращается в универсальное утверждение;
- неизвестность исчезает из ответа запроса и остаётся только в общей сводке;
- управляющая зависимость смешивается с источником передаваемого значения;
- автор контракта сам подтверждает его инженерную корректность.

## 5. Участники и ответственность

| Роль | Ответственность |
| --- | --- |
| Автор черновика | Агент `simintech-code`: собирает сведения, готовит первую версию таблицы и контрактов |
| Проверяющий семантику | Владелец как инженер SimInTech: проверяет соответствие реальному поведению блоков и модели |
| Проверяющий реализацию | Сопровождающий `simintech-code`: проверяет перенос в контракты, непротиворечивость графу и провенанс |

Правило: автор не подтверждает сам себе инженерную корректность. До проверки
строка таблицы имеет статус `preliminary`. Экспериментальные результаты
добавляются отдельными свидетельствами и не заменяют инженерную проверку.

## 6. Архитектурные решения

### 6.1. Один IR, а не второй

Отдельный Behavior IR не создаётся. Поведение расширяет существующие
сущности:

- `BlockContract` получает поля `behavior`, `dependencies`, `signal_types`;
- `SignalEdge` уже имеет `kind`, его значения используются как фильтр;
- `BehaviorSpec` ссылается на существующие идентификаторы Model IR и не
  копирует структуру модели.

### 6.2. BlockContract версии 2

Схема `block-contract/2`. Старые поля сохраняются. Новые поля необязательны:
отсутствие поля означает `unknown`, а не пустое значение.

```json
{
  "class": "Усилитель",
  "status": "measured",
  "ports": {"model": "fixed", "inputs": [{"index": 1, "name": "inport", "direction": "in"}], "outputs": [{"index": 0, "name": "outport", "direction": "out"}]},
  "behavior": {
    "operation": "gain",
    "expression": "y = a * u",
    "parameters": ["a"],
    "provenance": {"status": "derived", "ref": "catalog:060961f69db3"}
  },
  "dependencies": [
    {
      "output": 0,
      "source": {"kind": "port", "index": 1},
      "kind": "unconditional",
      "condition": null,
      "state": null,
      "provenance": {"status": "derived", "ref": "catalog:060961f69db3"}
    },
    {
      "output": 0,
      "source": {"kind": "property", "name": "a"},
      "kind": "unconditional",
      "condition": null,
      "state": null,
      "provenance": {"status": "derived", "ref": "catalog:060961f69db3"}
    }
  ],
  "signal_types": {
    "inputs": [{"index": 1, "type": "real", "unit": "unknown"}],
    "outputs": [{"index": 0, "type": "real", "unit": "unknown"}],
    "provenance": {"status": "unknown", "ref": ""}
  }
}
```

`dependencies` описывает только выходы своего класса. Связь между блоками
остаётся в графе: контракт не знает, какой провод пришёл на вход.

В примере `status: measured` относится к портовой модели. Поведение и
зависимости имеют `provenance.status: derived`, поэтому до утверждения строки
`contract` не выдаётся.

Поля `review` и `known_absences` дополняют запись:

```json
{
  "review": {"status": "preliminary", "reviewer": "", "date": ""},
  "known_absences": [
    {"output": 0, "source": {"kind": "port", "index": 2},
     "provenance": {"status": "claim", "ref": "pilot_blocks.yaml:Усилитель"}}
  ]
}
```

`known_absences` перечисляет проверенные отсутствия зависимости. Пустой
`dependencies` без заполненного `behavior` означает `unknown`, а не
«влияния нет».

### 6.3. Типы зависимостей

- `unconditional`: вход влияет на выход всегда.
- `conditional`: влияние зависит от условия; условие машиночитаемо.
- `control`: вход управляет выбором или режимом, но не передаёт значение.
  В `influence` это отдельный элемент: число на `number` не участвует в
  вычислении выхода, оно выбирает источник.
- `stateful`: влияние зависит от начального состояния или истории.
- `script`: поведение задано скриптом и не разобрано; влияние неизвестно.
  Это не только класс «Язык программирования»: если у экземпляра есть
  непустой скрипт в слоте `Script`, `OnInitScript` или `OnRunScript`,
  зависимости класса для этого объекта понижаются до `script` с причиной
  `object_script`. `OnDestroyScript` расчёт не меняет и в понижение не входит.
  В ответе `influence` это `kind: "script"` с `reason: "object_script"` и
  `evidence.status: "not_established"`, а не общий `unknown`.
- `unknown`: контракт не позволяет утверждать ни наличие, ни отсутствие связи.

Отсутствие зависимости не выводится из неудачного эксперимента. Оно может
следовать только из проверенного контракта с явным `known_absences`. Это
отдельный список, а не `kind`: отсутствие не является видом влияния.

### 6.4. Декларативные условия

Ограниченный набор операций, без исполнения произвольного кода:

```json
{"op": "equals", "source": {"kind": "port", "index": 0}, "value": 1}
{"op": "in", "source": {"kind": "property", "name": "mode"}, "values": [1, 2]}
{"op": "threshold", "source": {"kind": "port", "index": 0}, "above": 0.5}
{"op": "select", "source": {"kind": "port", "index": 0}, "cases": [{"value": 0, "input": 1}, {"value": 1, "input": 2}]}
```

Для классов с числом портов от экземпляра зависимости задаются ролями, а не
жёсткими индексами:

```json
{"source": {"kind": "port", "role": "all_inputs"}}
{"source": {"kind": "port", "role": "selected_input", "selector": {"kind": "port", "index": 0}}}
{"output": {"role": "all_outputs"}}
```

`dependencies_for(class_name, props)` разворачивает роли по фактическому
`nport` или весам `a`. Без этого Сумматор, Перемножитель, Мультиплексор и
Демультиплексор не представимы.

`nport_named` для коммутатора реализуется в тестовом контракте, а не в
production-реестре 958 классов: каталог его не содержит. Синтетическая
модель использует фиксированный экземпляр, а отдельный unit-тест проверяет
раскрытие `number` + `data_1..data_n`.

У коммутатора по номеру порта две записи: `control` для `number` и
`conditional` для `selected_input` с
`selector={"kind": "port", "role": "number"}`. `number` не становится
источником значения.

Если условие установить нельзя, `condition` остаётся `null`, `kind` остаётся
`conditional`, ставится `reason: condition_unknown`, а `evidence.status`
этого хопа будет `not_established`. Свободный текст в условии не допускается:
его нельзя проверить.

### 6.5. Состояние

```json
{"kind": "initial", "property": "x0"}
{"kind": "history", "window": "unbounded"}
{"kind": "memory", "cell": "..."}
```

`stateful` без описания состояния запрещён: это либо `unknown`, либо
незаполненный контракт.

### 6.6. Провенанс

Каждая зависимость и каждая строка эталона несёт:

```json
{"status": "measured|derived|claim|experiment|unknown", "ref": "..."}
```

- `measured`: живой замер реестра или выгрузки;
- `derived`: выведено из каталога, документации или кода;
- `claim`: утверждение инженера, проверенное и подписанное;
- `experiment`: наблюдение в конкретном прогоне;
- `unknown`: сведений нет.

Для эталонной таблицы дополнительно: `review.status` (`preliminary` или
`approved`), `review.reviewer`, `review.date`.

Правило выдачи `contract`:

- `measured` допускается только как измерение самого функционального
  отношения источник-выход, с ссылкой на это измерение;
- `claim` допускается только из строки с `review.status = approved`;
- `derived` допускается только при `review.status = approved`;
- `preliminary` даёт `not_established` всегда, даже если запись помечена
  `claim`.

`measured` в `BlockContract.status` или `ports.provenance` относится к
структуре: портам, числу входов, именам. Оно не подтверждает функциональное
влияние. Измеренный состав портов сам по себе даёт `not_established` для
зависимости: достоверность структурного измерения не переносится на
семантику.

`evidence.status = contract` возвращается, только если каждый хоп цепочки
проходит это правило. Иначе статус `not_established` с причиной `unapproved`.
Код не может подтвердить сам себя.

### 6.7. Типы рёбер и фильтрация

Существующие значения `SignalEdge.kind`: `wire`, `branch`, `boundary`,
`memory`, `block`.

- `wire`, `branch`, `boundary`, `memory` считаются структурными.
- `block` остаётся для связности, но в причинном запросе не используется как
  доказательство влияния.

Запросы `trace_signal`, `ancestors`, `descendants`, `find_path` получают
необязательный аргумент `edge_kinds`. По умолчанию поведение не меняется.
Новый запрос `influence` всегда отделяет структурные рёбра от `block`.

### 6.8. Запрос `influence`

Аргументы:

- `target`: адрес выхода (`объект:индекс` или имя объекта);
- `max_depth`: предел обхода, по умолчанию 64;
- `include`: какие статусы включать (`contract`, `not_established`);
- `max_items`: предел элементов, не больше 200.

Алгоритм:

1. Начать с целевого порта.
2. Идти назад по структурным рёбрам.
3. При входе в блок не проходить по `block`-ребру напрямую, а разрешать
   зависимости выхода по контракту блока.
4. Если контракт известен, добавить рёбра с типом зависимости и условием.
5. Если контракт неизвестен, добавить терминальный узел `kind: "unknown"` с
   причиной. Если поведение задано скриптом, добавить терминальный узел
   `kind: "script"` с `reason: "object_script"` и
   `evidence.status: "not_established"`. В обоих случаях путь не
   продолжается: ложная цепочка запрещена. Причина скрипта не сворачивается
   в общий `unknown`.
6. Для `stateful` добавить узел состояния.
7. Для внешней субмодели без страницы добавить `unknown` с причиной
   `external_submodel`.

Элемент ответа:

```json
{
  "target": "Двигатель:1",
  "source": {"kind": "port", "address": "Задатчик:0"},
  "path": ["Двигатель:1", "Регулятор:0", "Задатчик:0"],
  "hops": [
    {"from": "Регулятор:0", "to": "Двигатель:1", "kind": "conditional",
     "condition": {"op": "select", "source": {"kind": "port", "index": 0}, "cases": []},
     "state": null,
     "evidence": {"status": "contract", "ref": "block-contract:Коммутатор"}},
    {"from": "Задатчик:0", "to": "Регулятор:0", "kind": "unconditional",
     "condition": null, "state": null,
     "evidence": {"status": "contract", "ref": "block-contract:Усилитель"}}
  ],
  "evidence": {"status": "contract", "ref": "chain"},
  "unknown": null
}
```

Отдельно, вне `items`:

```json
{
  "known_absences": [
    {"target": "Двигатель:1", "source": {"kind": "port", "address": "Тормоз:0"},
     "provenance": {"status": "claim", "ref": "pilot_blocks.yaml:..."}}
  ]
}
```

Один элемент ответа - цепочка, а не отдельный хоп. `hops` хранит `kind`,
`condition`, `state` и провенанс каждого перехода. По худшему звену
агрегируется только `evidence.status`: наличие одного `unknown`-узла или
статуса `not_established` понижает весь элемент. Общий `kind` не выводится и
не подменяет типы хопов; если нужна сводка, она идёт отдельным полем и не
заменяет `hops`. Пример показывает форму после утверждения строк; до
утверждения те же хопы вернутся как `not_established` с причиной `unapproved`.

`known_absences` не входят в `items` и не являются терминальными узлами
влияния: это отдельный список проверенных отсутствий.

Адреса источников: `объект:порт`, `объект@property:имя`,
`объект@state:имя`, `объект@boundary:имя`, `объект@external:имя`.
Терминальные узлы: несоединённый вход, граница модели, свойство, состояние,
внешняя субмодель. Свойства и состояния входят в ответ, потому что у
«Константы» нет сигнальных входов, и без них ответ пуст.

Управляющая зависимость приходит отдельным элементом с `kind: "control"`.
Она не сливается с элементом выбранного входа: у первого в `source` стоит
`number`, у второго - `data_i`.

Статусы доказательства:

- `contract`: следует из проверенного контракта;
- `observed`: наблюдалось в эксперименте, с ссылкой на свидетельство;
- `not_established`: имеющихся сведений недостаточно.

В ответе `influence` статус `observed` не появляется: запрос не читает
эксперименты. `observed` возникает в отчёте приёмки, который сопоставляет
ответ с эталоном и свидетельствами. Так контракт и наблюдение не смешиваются.

Если путь содержит хоть один `unknown`- или `script`-узел, итоговый статус
не может быть `contract`.

### 6.9. `semantic_coverage`

Сводная характеристика, которая не заменяет локальную неизвестность:

```json
{
  "objects_total": 842,
  "objects_with_behavior": 610,
  "objects_with_approved_behavior": 8,
  "objects_with_known_ports": 700,
  "objects_unknown": {"script_defined": 20, "object_script": 5, "external_submodel": 11, "behavior_unknown": 201, "unapproved": 602},
  "dependencies_total": 1200,
  "dependencies_known": 800,
  "known_absences_total": 0,
  "paths_contract": 0,
  "paths_not_established": 0
}
```

`dependencies_total` считается после разворачивания ролей по экземпляру, а не
по статической записи реестра. `objects_with_approved_behavior` отделяет
утверждённые строки от `derived`.

Поля `paths_*` заполняются конкретным запросом `influence`, а не хранятся в
модели. Сводка по классам добавляется в `get_model_manifest`.

### 6.10. `BehaviorSpec`

Схема нужна, чтобы поведение всей модели не растворилось в контрактах блоков.
В пилоте она минимальна:

```json
{
  "schema": "behavior-spec/1",
  "model_hash": "...",
  "scenarios": [
    {"id": "speed_response", "target": "Двигатель:1", "inputs": ["Задатчик:0"], "checks": []}
  ]
}
```

`checks` в пилоте не исполняются. `BehaviorSpec` ссылается на `model_hash` и
адреса Model IR; структуру объектов он не дублирует.

### 6.11. Поверхность MCP

- `query_model(query="influence", arguments=...)`: новый запрос.
- `query_model(query="semantic_coverage")`: сводка по снимку.
- `get_model_manifest`: секция `semantics`, если она помещается в бюджет.
- `load_model`: `semantic_coverage` в компактном ответе.
- `inspect_submodel`: без изменений.

Новых инструментов не добавляется: поверхность остаётся компактной.

## 7. Пилотные классы

| Класс | Что уже известно | Что проверить в пилоте | Проверка |
| --- | --- | --- | --- |
| Константа | `fixed`, 0 входов, 1 выход, свойство `a` | Влияние параметра, отсутствие сигнальных входов | `live_acceptance` |
| Усилитель | `fixed`, 1 вход, 1 выход, свойство `a` | Безусловная зависимость от входа и параметра | `live_acceptance` |
| Интегратор | `fixed`, 1 вход, 1 выход, `k`, `x0` | Зависимость от истории и начального состояния | `live_acceptance` |
| Сумматор | `weights`, входы по `a` | Влияние каждого входа с весом | `live_acceptance` |
| Перемножитель | `nport`, 2 входа по умолчанию | Влияние всех входов, векторный режим | `live_acceptance` |
| Мультиплексор | `nport`, 6 входов по умолчанию | Векторный объединитель: каждый вход формирует компоненты выходного вектора; `selected_input` неприменим | `live_acceptance` |
| Демультиплексор | `weights`, 3 выхода по `a` | Влияние входа на каждый выход, правило распределения | `live_acceptance` |
| Язык программирования | `unknown`, `script_defined_ports` | Оставить `unknown` с причиной, не угадывать | `live_acceptance` |
| Ключ управляемый перекидной по входам тип 2 | `submodel`, `control` + `inport_1`/`inport_2`, в модели 1 экземпляр (`main/pwm::Macro171`) | Управляющая и условная зависимости через границу субмодели; обе ветви | `live_acceptance` |
| Коммутатор входных сигналов по номеру порта | `nport`, `number` + `data_1..data_n`, в модели отсутствует | Условный выбор по номеру; только независимая синтетическая модель | `synthetic_only` |

В модели девять живых классов: восемь базовых и ключ типа 2. Коммутатор по
номеру порта в модели отсутствует: инвентаризация 30.10.2026 дала 126
объектов и 27 классов, целевого класса среди них нет. Поэтому он проверяется
только на синтетической модели, и похожий класс его не заменяет: ключ типа 2
проверяет бинарный выбор, но не `number` и не `nport_named`.

Для сквозного объяснения через страницу ключа типа 2 нужен контракт
внутреннего `Ключ-3`: на странице `main/pwm/Macro171` стоит `Key3`. Это
вспомогательная запись эталона, она не входит в счёт десяти классов.

## 8. Эталон

### 8.1. Инженерная таблица

Файл `tests/fixtures/semantics/pilot_blocks.yaml`. Формат YAML выбран потому,
что таблицу читает и правит инженер, а не только код. PyYAML уже есть в
тестовых зависимостях. Файл публичен: это семантика классов, а не модель.

Для каждого класса фиксируются:

- порты и их роли;
- зависимости выходов от портов и свойств;
- тип влияния;
- условие и состояние;
- ограничения: что нельзя заключить;
- провенанс;
- статус проверки и проверяющий.

Строка без `review.status: approved` не участвует в приёмке как эталон.

В эталоне десять строк. У каждой есть `scope`: `live_acceptance` или
`synthetic_only`. В живой приёмке девять строк; коммутатор по номеру порта
остаётся `synthetic_only`. `Ключ-3` идёт вспомогательной записью для
сквозного объяснения через страницу ключа типа 2.

### 8.2. Контрольные вопросы

Публичный файл `tests/fixtures/semantics/synthetic_questions.yaml` строится
на независимой синтетической модели, а не на переименованном электроприводе.
Для каждого вопроса заранее фиксируются:

- целевой выход;
- ожидаемые входы;
- типы влияния;
- ожидаемые участки с неизвестной семантикой;
- утверждения, которые обязаны остаться неизвестными;
- ссылки на контракты и эксперименты.

Живые вопросы включают ключ типа 2 и обе ветви управления. Синтетические
вопросы включают коммутатор по номеру порта.

Вопросы к реальной модели и полный пакет приёмки остаются во внутреннем
хранилище: даже без имён структура, число блоков, параметры и траектории
раскрывают модель.

### 8.3. Экспериментальные свидетельства

Реальные прогоны и траектории остаются во внутреннем хранилище. Публичная
сводка допустима только для экспериментов на независимой синтетической
модели; её формат:

```json
{
  "id": "exp-speed-step-01",
  "structure_hash": "...",
  "content_hash": "...",
  "scenario": {"changed": "Задатчик:0", "from": 0.0, "to": 1.0, "at": 0.1},
  "run": {"step": 1e-6, "to_time": 0.5, "baseline": "exp-speed-base-01"},
  "observation": {"target": "Двигатель:1", "changed": true, "first_change_at": 0.1002},
  "status": "observed",
  "recorded_at": "2026-10-30"
}
```

Свидетельство без условий прогона и обоих хешей модели недействительно.
Расхождение `structure_hash` или `content_hash` с текущим снимком делает
наблюдение неприменимым: оно относится к другой модели. Реальные
свидетельства не публикуются даже с псевдонимами.

### 8.4. Экспериментальная установка

Эксперименты идут на копии `.prt`, исходная модель не изменяется. Для снятия
траектории используется блок «В файл» и `read_output_file`, либо `get_signal`
при подключённой базе сигналов. Каждый эксперимент имеет базовый прогон с
неизменёнными входами.

Для ключа типа 2 отдельный сценарий: различимые сигналы на `inport_1` и
`inport_2`, два состояния `control`, проверка обеих ветвей и прохождения
через границу субмодели. Точные значения `control` берутся из справки или
внутренней реализации; до установления они не заполняются.

Публичны семантика классов и тесты на независимой синтетической модели.
Реальная модель, её адреса, топология, параметры, траектории и полный пакет
приёмки остаются внутренними. Псевдонимы не делают свидетельство публичным:
структура соединений, число блоков, значения параметров и временные ряды
раскрывают модель и без исходных имён. Агрегированная сводка реальной
приёмки допускается в публичный репозиторий только после отдельной проверки
DATA_POLICY.

## 9. Тесты и приёмка

### 9.1. Unit

- Схема `block-contract/2` принимает десять пилотных записей.
- `influence` на синтетической модели: известный контракт даёт `contract`;
  неизвестный контракт даёт `unknown` и не продолжает путь.
- `edge_kinds` фильтрует рёбра; по умолчанию поведение прежнее.
- Условная зависимость сохраняет условие в ответе.
- `stateful` без состояния отвергается.
- `semantic_coverage` считает причины неизвестности раздельно.

### 9.2. Мутационные проверки

Тест обязан уметь упасть, если:

- `block`-ребро снова считается причинным;
- `unknown` заменяется на `contract`;
- условие теряется при сериализации;
- `preliminary`-строка проходит как `approved`;
- `derived`-зависимость возвращается как `contract`;
- структурный `measured` (порты, число входов) переносится на
  функциональную зависимость;
- `script` сворачивается в общий `unknown` и теряет `object_script`;
- `known_absences` попадает в `items` как источник влияния;
- общий `kind` подменяет типы отдельных хопов;
- свойство или состояние теряется на терминальном узле;
- роли `all_inputs`/`all_outputs` не разворачиваются по экземпляру.

### 9.3. Живые проверки

Только локально на Windows, вне CI. Оформляются отдельным набором и требуют
явного запуска. Отсутствие Windows-раннера не компенсируется зелёным CI.
Публичные тесты используют независимую синтетическую модель; прогоны на
реальной модели остаются внутренними.

### 9.4. Критерии приёмки

1. Найдены все зависимости, подтверждённые эталонной таблицей и проверенными
   сценариями.
2. Ни один структурный путь не объявлен доказанным функциональным влиянием.
3. Безусловные, условные и зависящие от состояния зависимости различены.
4. Неизвестные участки видны в ответе, у каждого существенного утверждения
   есть провенанс.
5. Инженер может проследить каждое утверждение до контракта или наблюдения и
   увидеть границу доказанного.

Живая приёмка покрывает девять классов; синтетическая - десять, включая
коммутатор по номеру порта.

## 10. Порядок работ

0. Закрыть текущую ветку `feat/submodel-viewer` в `simintech-mcp`: фикс
   `d81806f` не влит.
1. Схема контрактов v2 и десять черновых записей. Проверка схемы и unit-тесты.
2. `edge_kinds` в запросах графа, запрос `influence`, `semantic_coverage`.
3. Секция `semantics` в паспорте и компактном ответе `load_model`, MCP-обвязка.
4. Черновик инженерной таблицы и публичных синтетических вопросов. Проверка
   владельцем. Вопросы к реальной модели остаются во внутреннем хранилище.
5. Перенос утверждённых строк в контракты (`provenance.status = claim`,
   ссылка на строку таблицы) и тест на расхождение таблицы и контракта.
   Правки идут через `generate_block_contracts.py --merge`: полный `generate`
   перезаписывает все классы и не должен терять поля v2.
6. Внутренние эксперименты на копии модели, сводки свидетельств и
   независимая синтетическая модель для публичных тестов.
7. Приёмка по критериям раздела 9.4.

Шаги 1 и 2 можно вести параллельно после согласования схемы.

## 11. Риски и открытые вопросы

- Коммутатор по номеру порта в модели отсутствует (инвентаризация 30.10.2026:
  126 объектов, 27 классов). Он остаётся `synthetic_only`. Ключ типа 2
  проверяет бинарный выбор через границу субмодели, но не заменяет `number`
  и `nport_named`.
- Для сквозного объяснения через страницу ключа типа 2 нужен контракт
  внутреннего `Ключ-3`; без него путь оборвётся на `unknown`.
- Мультиплексор остаётся векторной операцией без управляющего входа.
- Публикация: псевдонимы не защищают свидетельство. Публичные тесты идут на
  независимой синтетической модели; реальная приёмка и её полный пакет
  остаются внутренними.
- Шаг модели 1 мкс: длинные прогоны дороги. Сценарии должны быть короткими и
  воспроизводимыми.
- Внешняя библиотечная субмодель: в модели привода одна (инвентаризация
  30.10.2026). Пути через неё остаются `unknown`, пока страница не раскрыта.
  Это допустимо для пилота, но должно быть видно в ответе.
- Эталон может быть неполным. Неполнота фиксируется как `unknown`, а не
  заполняется догадкой.
- YAML удобен инженеру, но добавляет второй формат рядом с JSON-контрактами.
  Это осознанный выбор: таблицу правит человек.
- `block_contracts.json` генерируется. Полный прогон генератора без `--merge`
  перезапишет `behavior`/`dependencies`; тест на дрейф обязателен.
