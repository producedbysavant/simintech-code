# Семантический слой модели: контракт первого среза

Спецификация Milestone 4.1. Реализация первого среза — M4.2 (структуры) и M4.3
(`model_overview`); остальные пункты очереди перечислены здесь как **не входящие**.

## Вопрос, на который отвечает слой

> **«Что представляет собой эта модель и как она устроена?»**

Из этого вопроса выведен минимальный слой, а не из «какие методы COM ещё можно
завернуть»:

```
model_overview
    ↓
containers / hierarchy      ← в первом срезе только описание самого контейнера
    ↓
objects → ports
    ↓
connections
```

## На чём стоит слой: только доказанные примитивы

| Уровень | Что уже есть | Статус |
|---|---|---|
| Объекты контейнера | `Topology.objects` (`ObjectRow`: имя, класс) | **измерено** — совпадает с эталоном вендора поимённо |
| Порты | `Topology.ports` (`PortRow`: объект, индекс, направление, имя) | **измерено** — направления сверены с `GetPortInfo().Mode` |
| Связи | `Topology.connections` (`Connection`: неориентированные концы) + `connection_key` | **измерено** — 32 связи на демо, совпадение с эталоном по ключам |
| Сам контейнер | `Project.get_main_page()`, `Project.get_current_page()`, `Page.activate()`, `Project.submodel_page(block_id)` | **успешный путь измерен** на демо: `acrms_Circuit1`, 35 объектов |
| Получение данных | `read_topology(client, project_id, result_path)` | **измерено** |
| Метаданные порта сверх протокола (`PortInfo`, координаты) | `Port.get_info()` | измерено как структура; **в первый срез не входит** |
| Перечисление контейнеров | — | **в COM метода нет** |
| `Page.parent()` | предполагается `PageUp` | **не измерено** |
| Субмодели глубже одного уровня, различие `load_submodel`/`assign_submodel` | — | **не измерено** |
| Группа рестарта (8 методов) | — | **не проверена на живом SimInTech** |

Отсюда два следствия для контракта, и оба — не стилистика:

1. **Идентификатора контейнера среда в Python не отдаёт.** `getcurrentcontainer` и
   `getownercontainer` существуют только **внутри тела пробы**; COM-метода
   «какой контейнер текущий» нет. Поэтому контейнер описывается **путём, которым
   его получили** (`ContainerRef`), а не собственным идентификатором. Данные же
   описывают тот контейнер, который текущий по мнению среды, — это доказано
   живыми тестами (`test_objects_match_com`,
   `test_probe_matches_vendor_reference_inside_container`).
2. **Иерархия не входит в первый срез.** Вложенность субмоделей не измерена ни на
   одном уровне, кроме одного; `Page.parent()` — предположение; перечисления
   контейнеров нет вовсе. Строить `hierarchy` в контракте раньше замера значило
   бы объявить семантику, которой у нас нет.

## Контракт

```python
ContainerRef(kind, block_id=0, block_name="")   # kind: "main" | "submodel"
PortView  — не вводится: порт — это `PortRow` топологии
ObjectView(name, class_name, ports)             # группировка портов по объекту
ModelOverview(container, objects, connections)  # connections — `Connection` как есть
```

Осознанные решения:

* **Связи берутся из топологии как есть, без нового типа и без новой дедупликации.**
  `Connection` уже означает «что с чем соединено» и уже хранит предупреждение, что
  это *не* восстановление проводки. Второй тип с тем же смыслом разошёлся бы с
  первым молча.
* **Порты не переупаковываются** в новый тип: `PortRow` уже несёт `object_name`,
  который внутри `ObjectView` избыточен, но заведение параллельного типа ради
  экономии поля создало бы два описания одного и того же.
* **Слой не делает новых COM-вызовов.** `read_model_overview` вызывает
  `read_topology` и проецирует результат; всё остальное — чистая функция. Это
  проверяется стражем: юнит-тест подменяет `read_topology` и требует, чтобы обзор
  собирался из него, а транспорта слой не касался.

### JSON-форма (для будущего MCP-адаптера)

```json
{
  "container": {"kind": "submodel", "block_id": 7, "block_name": "acrms_Circuit1"},
  "summary": {"objects": 35, "ports": 68, "connections": 32},
  "objects": [
    {"name": "Integrator_0", "class_name": "Интегратор",
     "ports": [{"index": 0, "direction": "in", "name": "Вход"}],
     "counts": {"in": 1, "out": 1, "undirected": 0}}
  ],
  "connections": [{"a": ["Integrator_0", 0], "b": ["Step_source_1", 0]}]
}
```

Числа в примере — форма, а не замер; замер идёт живым тестом на демо.

## Границы, которые контракт обязан называть

* **`connections` — «что с чем соединено», а не «как проложено».** Кратность взята
  у вендорского экспортёра (на входной порт — один сосед), поэтому форма линии
  теряется: ветвление двумя `connect` и `branch_to` дают одно и то же множество
  связей. Для анализа проводки нужен wire-level API, достаточность которого **не
  доказана**.
* **Контейнер — это область обзора, а не объект модели.** Имя и id — это путь
  (`ContainerRef`), а не свойство контейнера.
* **Один уровень внутрь и только успешный путь.** Ветка отказа `submodel_page` на
  живом SimInTech не измерялась; различия `load_submodel`/`assign_submodel` — тоже.
* **Объект «комментарий» критерием не отличается от модельного** (тип 100, ноль
  портов) — это уже зафиксировано в топологии.

## Что не входит в первый срез

Очередь Milestone 4 целиком (M4.1–M4.9) остаётся в силе, но **первый PR — это
M4.1–M4.3 одной вертикалью**, а не девять отдельных веток:

| # | Что | В первом срезе |
|---|---|---|
| M4.1 | semantic contract (этот документ) | **да** |
| M4.2 | структуры Model / Container / Object / Port / Connection | **да** |
| M4.3 | `model_overview` | **да** |
| M4.4 | `inspect_object` | нет |
| M4.5 | `inspect_port` | нет |
| M4.6 | `query_connections` | нет |
| M4.7 | hierarchy / containers | нет — семантика не измерена |
| M4.8 | diagnostics / validation | нет |
| M4.9 | diff / query primitives | нет |

Отдельные очереди, которые этот срез **не блокируют** и которые в него не тянутся:
типы `105/109/113`, тип `111`, оставшиеся continuation-paths, wire-level
реконструкция, семантика первого соседа `traceallports`. Изменение модели
(`editing`, `delete/add/reconnect`, транзакции, откат) — Milestone 6, **после**
read-side API.

## Границы репозиториев

```
simintech-code   semantic representation и query primitives   ← здесь
      ↓
simintech-mcp    тонкий адаптер: MCP request → semantic query → structured result
      ↓
simintech-skill  после стабильного контракта: как спрашивать модель
```

`simintech-mcp` не должен знать внутренностей COM и топологии: он получает
структуры и отдаёт их как ресурс или инструмент. `simintech-skill` подключается
после того, как контракт стабилизируется, — учить агента спрашивать раньше, чем
есть что спрашивать, значит закрепить в скилле промежуточную форму.

## Тестовые опоры

* **Без COM** — тот же паттерн, что уже принят в репозитории: локальный фейк с
  записью вызовов и `monkeypatch` на транспортной границе (`tests/unit/test_topology.py`
  подменяет `ScriptBridge`); для семантического слоя подменяется `read_topology`.
* **Живьём** — копия демо вендора, вход в контейнер `acrms_Circuit1`, сверка с
  эталоном (`tests/vendor_reference.py`) по именам объектов и ключам связей, а не
  по числам, вбитым константой. Живой тест не импортирует помощников из соседнего
  живого файла: живые тесты не зависят друг от друга.
