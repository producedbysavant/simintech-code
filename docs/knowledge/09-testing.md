# 09. Тестирование: unit, live, негативные и мутационные проверки

Раздел базы знаний (индекс — `README.md`). Правила проверок, которые в этой
экосистеме уже ловили реальные дефекты, и границы того, что тесты доказывают.

## Четыре уровня и что каждый доказывает

| Уровень | Где | Что доказывает | Что НЕ доказывает |
|---|---|---|---|
| unit-fake | `tests/unit/**` (фейки — `_support`-стиль) | Контракт кода: переходы состояний, отказы, маршрутизация | Поведение SimInTech: подделка повторяет наше допущение |
| unit-pure | там же | Чистый разбор (геометрия, парсеры, сборка тел) | Связь с реальностью за пределами разбора |
| distribution | там же (фикстуры из поставки) | Соответствие данным поставки (каталог, .pak/.tbl/.xprt) | Живое поведение COM |
| live | `tests/integration/**` (маркер `integration`) | Поведение среды на Windows | Ничего, пока не исполнен: `live-tests-run-only-locally` — в CI живых тестов нет |

**Факт и граница:** `live-tests-run-only-locally` (code-confirmed) —
Windows-раннера нет; зелёный CI не означает «проверено на SimInTech».
Смешивать уровни нельзя: `unit-fake` не поднимает статус факта выше
`code-confirmed` — это правило реестра, а не пожелание.

## Правила, которые уже ловили дефекты

1. **Фейк моделирует переход, а не подставляет ответ.** Подделка, отвечающая
   одинаково на два разных вызова («время всегда растёт»), кодирует то же
   допущение, что и код, и опровергнуть его не может. Держите тест на
   **ненулевом** начальном состоянии (у моста — `FakeEnv` с двумя страницами,
   иначе замеренный дефект «стирается скрипт неглавной страницы» не
   воспроизводился бы).
2. **Гейт считается рабочим только после проверки мутацией.** Тест, который
   не падает при снятии защиты, — декорация. В этом репозитории так проверен
   каждый защитный механизм (снятие проверки источника линии, потеря чистки
   реестра, подмена якоря пина и т.д.); на ревью спрашивайте «какая мутация
   его красит».
3. **Отрицательные образцы.** У гейта данных (`public_data_check`) тесты
   содержат и «поймай это», и «не тронь это»: правило, краснеющее на своей
   же документации, отключают.
4. **Живой тест гасит только свои процессы.** Вывод — `[simintech] … лишние
   погашены`; чужой `mmain.exe` не трогается никогда: «лишний на вид»
   процесс может быть живым SimInTech пользователя с несохранённой моделью.
5. **Живые сверки — против внешнего эталона, а не сами с собой.** Эталон
   топологии (`tests/integration/fixtures/vendor_topology_reference.json`) —
   выгрузка вендорского скрипта, снятая нашим прогоном; канонизация связей в
   тесте реализована независимо от библиотечной (`connection_key_of`).

## Как запускать

```bash
python3.11 -m pytest tests/unit -q                      # без COM, идёт в CI
python3.11 -m pytest tests/integration -m integration -q  # Windows + COM
python3.11 -m pytest -m distribution -q                 # сверка с поставкой
python3.11 -m pytest -m performance -q                  # бенчмарки (стенные часы)
```

Живые тесты дополнительно требуют опции `--run-simintech` (или фикстуры
`simintech_available`) и зарегистрированного `mmain.exe /regserver`; без
демо-проектов поставки часть тестов честно скипается с названной причиной.

## Процедура правки (обязательная)

1. Правка поведения — с тестом; тест сначала красный (мутация приветствуется).
2. Для COM-путей приложение: живой прогон при первой возможности; в описании
   PR — **честно**, был ли он. «Тесты на фейке проверяют разбор, а не
   поведение среды» — формулировка из `CLAUDE.md`, держите её буквально.
3. После правки — обновить реестр (`docs/evidence/claims.yaml`): новые факты,
   опровергнутые — в `contradicted` с `contradicted_by`.
4. Живая приёмка библиотеки, меняющей контракт для MCP, — на голове main
   после перезапуска сервера (MCP держит код ревизии запуска).
