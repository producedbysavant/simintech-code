# COM-интерфейс SimInTech

Внешний программный интерфейс SimInTech — COM-сервер `IMVTU_Server`.
Работает **только в Windows**: сервер `mmain.exe` запускается отдельным
процессом (out-of-proc), на Linux и в WSL COM недоступен.

Доступ к интерфейсу из Python — через библиотеку `comtypes`, не через
`pywin32`. Причина принципиальная: тип `TDataDescriptor` маршалится как
`VT_RECORD`, с которым `pywin32` не справляется. Попытка работать через
`pywin32` приводит к ошибкам на уровне типизации.

## Подключение

COM-сервер нужно зарегистрировать в системе — это делается один раз:

```
mmain.exe /regserver
```

Далее клиент создаёт объект по ProgID и подключается. Идентификаторы:

| Что | Значение |
|-----|----------|
| ProgID | `mmain.MVTU_Server` |
| CLSID | `{ACE730D7-1712-4C70-87C8-7E4C55622E91}` |

> ⚠ Встречается упоминание ProgID `MVTU.Server` — оно **не работает**.
> Если создание объекта падает, перебирайте кандидатов: сначала
> `mmain.MVTU_Server`, затем CLSID.

При подключении полезно сразу попросить сервер не показывать окна и не
закрываться:

- `SetNoCloseAppFlag(1)` — сервер не завершится сам, пока клиент не решит;
- `SetSilentMode(1)` — без диалогов.

## Порядок вызовов

`ProjectStart` **обязателен** перед чтением списка сигналов: без него
модель не скомпилирована, и список будет пуст.

```python
import comtypes.client

server = comtypes.client.CreateObject("mmain.MVTU_Server")

server.SetNoCloseAppFlag(1)
server.SetSilentMode(1)

proj = server.OpenProject(r"C:\path\to\model.prt")
server.ProjectStart(proj)      # без этого сигналы не прочитаются
server.ProjectRun(proj)
```

Пакет проектов открывается через `OpenPack`, а проект внутри пакета
достаётся по индексу: `PackGetProjectIdByIndex(pack_id, index)`.

Расчёт в непрерывном режиме без остановки «подвешивает» вызов — используйте
запуск до заданного времени и явную остановку, а не бесконечный `run`.

## Сохранение и выгрузка

| Метод | Назначение |
|-------|-----------|
| `SaveProjectXML` | Выгрузить проект в `.xprt` (XML) |
| `SaveProjectBinary` | Сохранить проект в `.prt` (бинарный) |
| `ExportDBToXML` | Выгрузить базу сигналов в XML |

Первые два — основа работы с проектом как с текстом: `.prt` бинарный и
редактором не правится, поэтому схему выгружают в `.xprt`, разбирают и
правят, а затем собирают обратно (`OpenProject` → правка → `SaveProjectBinary`).
Форматы описаны в `file-formats.md`.

`ExportDBToXML` делает то же для базы сигналов, что макрос `dbexporttoxml`
(см. `signal-db.md`).

## Работа с сигналами

### Список сигналов

`GetProjectSignalList` возвращает **только внешние (обменные) сигналы** —
те, что выведены через блоки «Вход/Выход алгоритма». Сигналы внутри схемы
в этот список не попадают. Поэтому **пустой список — не ошибка**: у модели
без внешних интерфейсов он и должен быть пустым.

Чтобы получить имена внутренних сигналов, модель выгружают в `.xprt`
и разбирают XML — этот путь даёт имена всех блоков
(см. `file-formats.md`).

### Дескриптор данных

Сигнал описывается структурой `TDataDescriptor`:

| Поле | Тип | Смысл |
|------|-----|-------|
| `DataId` | int64 | Идентификатор сигнала; `0` означает «не найден» |
| `DataType` | long | Тип данных |

Значения `DataType` официально не документированы — они восстановлены
по практике:

| Значение | Тип |
|----------|-----|
| 0 | double |
| 1 | integer |
| 2 | bool |
| 4 | string |
| 5 | массив double |
| 12 | массив integer |

Обратите внимание: значение `3` пропущено.

### Чтение и запись

Метод выбирается по типу сигнала:

| Тип | Чтение | Запись |
|-----|--------|--------|
| double | `ReadAsFloat` | `WriteAsFloat` |
| integer | `ReadAsInteger` | `WriteAsInteger` |
| bool | `ReadAsInteger` | `WriteAsInteger` |
| string | `ReadAsString` | `WriteAsString` |

Логический тип читается и пишется как целое.

Массивы — поэлементно:

| Тип | Чтение элемента | Запись элемента |
|-----|-----------------|-----------------|
| double[] | `GetExtArrayElement` | `SetExtArrayElement` |
| integer[] | `GetIntArrayElement` | `SetIntArrayElement` |

Размер массива — `GetArrayCount` / `SetArrayCount`.

Поиск сигнала по имени — `FindDataInListByName`. Надёжность поиска зависит
от того, как сигнал зарегистрирован в проекте: не рассчитывайте, что любой
сигнал схемы найдётся по имени блока.

## Состояние проекта

`GetProjectStateFlag` возвращает битовую маску:

| Значение | Состояние |
|----------|-----------|
| 0 | остановлен |
| 1 | инициализирован |
| 3 | выполняется |
| 7 | пауза |
| 9 | ошибка |

## Создание блоков

Порядок вызовов при сборке схемы из кода:

1. `CreateBlock` — создать блок класса;
2. `InitBlock` — инициализировать;
3. `SetBlockProp` — задать свойства;
4. `SetBlockPosition` — разместить.

Связь создаётся через `CreateWire` с нулевым числом точек, после чего
вызывается `NormalizeWire` — она прокладывает линию автоматически.

### Имена свойств блоков

Ниже — имена свойств, сверенные с каталогом
`simintech_api/data/block_catalog.json` (источник истины). Это же написание
используется в диалоге свойств блока, поэтому таблицы применимы не только
к COM.

| Класс блока | Свойства |
|-------------|----------|
| `Константа` | `a` — значение |
| `Усилитель` | `a` — коэффициент |
| `Сумматор` | `a` — массив коэффициентов (веса входов); число входов задаётся портами (`SetPortCount`), а не свойством |
| `Интегратор` | `k` — коэффициент, `x0` — начальное условие |
| `Производная` | `x0` — начальное условие |
| `Ступенька` | `t` — момент срабатывания, `y0` — значение до, `yk` — значение после |

Значения свойств передаются **строками**:

| Тип значения | Как передавать |
|--------------|----------------|
| число | компактно, без лишних нулей: `2.0` → `"2"` |
| логическое | `"1"` или `"0"` |
| массив | `"[1, 2, 3]"` |

### Классы, которые отвергает библиотека

Две записи — «Из памяти» и «Порт выхода» — входят в
`UNSUPPORTED_COM_BLOCK_CLASSES` (`simintech_api/constants.py`), и попытка
`Page.create_block` приводит к `UnsupportedBlockError`. Это защита библиотеки,
а не отказ COM: замерено на живом COM 2026-09-18 — `CreateBlock` создаёт обе
записи и возвращает ненулевой id, блок появляется на странице, свойства
читаются («Из памяти» → `FromMem_0` с `a`/`src_type`, портов нет; «Порт
выхода» → `PortConnector_0`, один порт). Годятся ли эти блоки в модели, не
проверено, поэтому защита оставлена. Такие участки собирайте вручную или через
субмодели.

Блоки библиотеки «Конечные автоматы» — другой случай, и раньше здесь было
записано неверно: они **создаются**, но только по полному имени записи с
префиксом «Конечные автоматы - » (`FSM_BLOCK_RECORDS`). Короткий заголовок с
палитры («Состояние автомата») `CreateBlock` не принимает и возвращает 0.
Полный автомат через COM не собрать: состояния живут на внутренней странице
карты, а метода для неё в интерфейсе нет.

## Перехват журнала

SimInTech может отдавать свой журнал через именованный канал (named pipe).
Клиент в этой схеме — сам SimInTech, а приложение-приёмник создаёт канал
и слушает его. Включается парой вызовов: `SetPipeName(имя)` и
`SetJournalSavePeriod(мс)`.

## Предостережения

- **Сервер не завершается сам.** `CloseProject` закрывает проект, но процесс
  `mmain.exe` остаётся. Отслеживайте идентификаторы запущенных процессов
  и завершайте только свои — иначе рискуете убить чужой сеанс работы.
- В интерфейсе порядка 176 методов; результаты возвращаются через
  выходные параметры, идентификаторы — 64-битные целые.
- Идентификаторы портов нумеруются **с нуля**, в отличие от массивов
  в языке блоков, где индексация с единицы.
- Размер блока по умолчанию — 60×40. Сторона порта: `LEFT=0`, `RIGHT=1`,
  `TOP=2`, `BOTTOM=3`; режим: `INPUT=0`, `OUTPUT=1`.
- Типы, не описанные в официальной документации, восстановлены по практике.
  При обновлении SimInTech их стоит перепроверить — нумерация может
  измениться.
